# Battle Chronicles - combat end cleanup.
#
# DO NOT put an `effect = { }` block in here.
#
# on_action `events = { }`, `random_events = { }` and `on_actions = { }` are
# additive lists and merge across files. `effect = { }` DOES NOT. The engine keeps
# exactly one and logs
#   [E][jomini_onaction.cpp:161]: There is more than one 'effect' defined using most recent: file: ...
# and "most recent" is decided by file read order inside common/on_action, which
# is ALPHABETICAL - not playset load order. A mod loading dead last still loses to
# `combat_on_actions.txt` if its own filename sorts earlier. This exact bug ate a
# whole probe run on 2026-08-12.
#
# So: hook via `events = { }` and put the logic in a hidden combat_side event.
# That is what vanilla itself does (on_combat_end_winner -> combat_event.0001).
#
# THE `zz_` PREFIX IS LOAD-BEARING. The same alphabetical read order that decides
# an `effect` fight also decides the ORDER OF THE MERGED `events` LIST, and
# bc_chronicles.0091 has to be dispatched AFTER combat_event.1001 - the event that
# kills the losing side's knights - or its dead-knight toast finds a field on which
# nobody has died yet. Under the old name `bc_on_actions.txt` it sorted before
# `combat_on_actions.txt` and the toast logged ZERO over 112 grader runs.
#
# Renaming this file is therefore a behavioural change, not housekeeping. If it is
# ever renamed back, `BC: dead knights` goes silent again.

on_combat_end_winner = {
	events = {
		bc_chronicles.0091
	}
}

on_combat_end_loser = {
	events = {
		bc_chronicles.0092
	}
}

# on_combat_start IS DELIBERATELY UNCLAIMED, AND THIS PARAGRAPH IS WHY.
#
# The mod hooked it once, with a hidden `scope = combat` event that reached both
# sides through every_combat_side and each side's commander through
# side_commander. Measured over 22 qualifying combats: the event fired 22 times,
# the iteration ran 44 times - exactly two sides per combat, so BOTH links worked
# - and side_commander produced a commander ZERO times. The same side_commander
# reached a commander 227 times in the same session from mid-battle call sites.
#
# THE HOOK IS NOT BROKEN. NOBODY IS THERE YET. No commander is assigned to a
# combat side at on_combat_start, so no route from this hook can reach one, and
# combat_attacker / combat_defender were very likely never the problem either.
#
# The opening therefore moved into the battle - it is raised from the end of
# bc_battle_open_effect, on the first moment. Do not re-claim this hook for
# anything that needs a commander.
