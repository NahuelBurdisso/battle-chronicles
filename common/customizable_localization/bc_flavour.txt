# Battle Chronicles - prose fragments.
#
# THE ARMS ONLY COMPARE A RECORDED CLASSIFICATION. Every classification decision
# was made in an effect - bc_write_ground_effect and bc_write_bond_effect in
# bc_context_effects.txt, the size ladder inside bc_battle_open_effect in
# bc_ledger_effects.txt - where it could be logged. Nothing here decides
# anything; it selects a sentence for a decision already recorded. So a fragment
# that renders wrong is two different bugs, and the marker in the log tells them
# apart: if the marker names the band you expected, the fault is in this file -
# arm order, comparison value, comparison form, or loc key - and if it does not,
# the effect classified wrong and this file rendered faithfully. Do not narrow
# the first half to arm order: the scale header below documents a fault of the
# comparison FORM that leaves the marker correct and the arm order correct.
#
# MOST OF THOSE COMPARISONS ARE AGAINST A FLAG. bc_scale_clause is the exception
# and compares a NUMBER, because bc_battle_size is written as one. Its own header
# says what that costs.
#
# CITATIONS INTO bc_ledger_effects.txt NAME A PARAGRAPH, NOT A LINE, AND THAT IS
# A RULE RATHER THAN A STYLE. That file's comments are long and get edited often,
# so every edit shifts every line below it. Rounds 7 and 8 both spent their
# headline finding on prose that had ROTTED rather than on prose that was wrong
# when written, and round 8's was this exact failure. In 253e4f7 two comments
# grew by three lines between them; most of the citations below were re-pointed
# correctly and a handful were not, and the ones that were not landed on an
# `exists` guard, a debug_log line, a paragraph tail, and the `A BUCKET, 1/2/3`
# heading itself. Read the commit if the detail matters. No count appears here
# on purpose: three rounds running, this paragraph asserted how many were wrong
# and was itself wrong, because the answer depends on whether a bare `:472`
# continuing a previous citation counts as one. That is the whole argument in
# miniature - a number about line numbers is as brittle as the line numbers.
#
# A name like `THE ABSENT SIZE CASE IS REAL` or `A BUCKET, 1/2/3` cannot rot
# silently: grep either finds it or the paragraph was renamed, which is a
# visible event. Note that landing on a heading is not the same as naming one,
# and only the name is checkable. `validate` now flags a citation that lands on
# a blank line, a bare `#`, a `}` that is not the end of a range, off the end of
# a file or below line 1, a range that runs backwards, a `bc_` file this mod
# does not have, and - as a warning - a basename more than one file here
# carries. That is all eight of them; the authoritative list is the WHAT THIS
# CHECKS IS POSITION, NOT MEANING comment in tools/ck3lib/validate.py. What it
# cannot flag is a citation landing on the wrong LIVE line, which is the case
# round 8 lost its headline to. Not `--strict`: that flag only adds the
# missing-loc check, and the citation check runs on every validate.
#
# THE RULE IS ABSOLUTE FOR bc_ledger_effects.txt AND ASPIRATIONAL EVERYWHERE
# ELSE, and saying so is more honest than a rule this file breaks. Below there
# are still line citations into bc_script_values.txt, bc_eve_events.txt,
# bc_eve_effects.txt, bc_scripted_effects.txt and the two phase-event files, and
# none of those is edited rarely either - bc_script_values.txt has 8 commits,
# bc_commander_phase_events.txt 7, bc_knight_phase_events.txt 8. No count of
# them appears here: it changes every time a paragraph is converted, and a
# number that goes stale in the paragraph forbidding stale numbers is a joke
# this file has already told three times. Grep for `.txt:` if you need the
# figure. They get converted as the paragraphs around them are touched, not in
# a sweep, because a sweep of citations is the exact edit that went wrong in
# round 8 - and the five that this round converted, into bc_context_effects.txt,
# had been three lines stale since aef7f41, the very commit that wrote this
# rule. For same-file references the rule is already absolute: name the key.
#
# ONE EXEMPTION, and it is not a loophole: a citation recording where a marker
# WAS in a build that has since moved on. README.md's `Family 3 is shipped but
# unmeasured` section does this - it quotes a log line against
# `bc_ledger_effects.txt:258` and labels it a previous build. A paragraph name
# cannot express a pointer into a superseded file, and the number is not a claim
# about the current one. Anything that IS a claim about the current file follows
# the rule.
#
# type = character ON EVERY DEFINITION, and invoked on a SAVED SCOPE, never on a
# variable-held character. Vanilla's Custom2 second argument is always a saved
# scope or ROOT.Char - a variable-held character has zero uses in vanilla or
# AGOT - so the mod does not use Custom2 at all.
#
# THE FALLBACK ARM IS LAST AND HAS NO TRIGGER. CK3 takes the first matching arm
# in order, so a trigger-less arm anywhere but last would swallow the ones below
# it. Every definition here ends in one.
#
# HOW OFTEN THAT FALLBACK ACTUALLY RENDERS VARIES BY DEFINITION AND BY CALL SITE.
# The ground case is stated here rather than in bc_banner_falls_ground's header,
# which is a spike marker and says nothing about its fallback; every definition
# added from bc_bond_clause onward states its own. On the ground clauses the
# fallback is load-bearing from anywhere, because bc_write_ground_effect removes
# the variable first and has two exits that never rewrite it. On bc_bond_clause
# it never renders from the ten moment toasts, because bc_write_bond_effect
# writes on every path and runs upstream of all ten - but it would render from a
# pop-up option's toast whose option is ANSWERED after the combat ended, because
# that is the case in which bc_clear_scratch_effect has already run (the KNOWN
# LEAK paragraph above that effect in bc_ledger_effects.txt). Note the verb: what
# the close of that paragraph calls the normal case is the pop-up ARRIVING
# mid-battle, and a pop-up answered when it arrives still finds the variable
# there. No pop-up option toast exists yet.
#
# SO CHECK THE WRITER **AND** THE CALL SITE. Checking only the writer gives the
# wrong answer for the pop-up case, and no fallback here may be deleted on the
# strength of a claim that names only one of the two.
#
# NESTED, NOT SIBLING, on the variable read. The bare `exists` row and the
# trigger_if are safe as siblings - only the READ has to be nested, which is
# what the trigger_if does. A `trigger_if` whose `limit` fails evaluates TRUE,
# so the bare `exists` beside it is the row that actually rejects.

# --- SPIKE. The only WIRED fragment set. -------------------------------------
#
# It was written to prove the shape renders before the other 103 fragment keys
# were, and that run has not happened. bc_bond_clause and bc_scale_clause below
# it were written anyway, under the AMENDMENT in
# docs/plans/2026-08-15-battle-chronicles-depth-plan-b-prose.md, which split the
# gate: a clause APPENDED to a desc that keeps its literal sentence fails to "no
# improvement", so it needs no run, while a clause that REPLACES the literal
# fails to an empty toast and still does. This spike is the only fragment set any
# call site names today.
bc_banner_falls_ground = {
	type = character

			exists = var:bc_battle_ground

# --- the bond, shared by all ten moments -------------------------------------
#
# SHARED AND NOT PER-MOMENT, unlike the per-moment ground clause above (one so
# far, and a spike). A clause about the foe reads the same after a banner falling
# as after a flank collapsing; a clause about the ground does not - a standard
# goes down IN the sand, a flank collapses AMONG the trees. The verb has to agree
# with the ground and does not have to agree with the foe. That is the whole
# reason this is one definition and the ground will be ten.
#
# FIVE VALUES, MATCHING bc_write_bond_effect'S LADDER EXACTLY: nemesis, kin,
# countryman, heathen, stranger. `stranger` gets a real clause rather than
# sharing the fallback because it is a real answer, and the reason is the LADDER'S
# TERMINAL ARM, not the leaderless one: bc_context_effects.txt's `THE LADDER HAS
# A TERMINAL ARM AND IT IS NOT DECORATION` paragraph records that a foe of a
# different culture and the same faith - the largest match-up class on the AGOT
# map - lands there. The outer `else` in bc_write_bond_effect, the one that logs
# `BC: bond nofoe`, routes a LEADERLESS enemy side to the same value, but that
# arm justifies itself by saying the prose has a stranger clause, so citing it
# alone argues in a circle. It is also only one half of the value, and the
# smaller one - the `MARKERS: SIX bond markers` paragraph warns not to read
# `nofoe` as a subset of `stranger` but as the OTHER half of it, and the
# terminal arm is the half that carries the largest match-up class.
#
# THE ORDER OF THOSE FIVE IS NOT THE ORDER THE EVE USES, deliberately. The eve's
# desc chain runs nemesis, kin, heathen, countryman, stranger; the ladder in
# bc_write_bond_effect runs nemesis, kin, countryman, heathen, stranger. This
# clause renders whatever the LADDER decided, so once it is wired a same-culture
# different-faith foe will read `countryman` in the toasts and `heathen` in the
# eve, in the same battle. That is the documented intent - see the reciprocal
# notes under bc_context_effects.txt's `DO NOT "RECONCILE" THIS LADDER WITH THE
# EVE` and at bc_eve_events.txt:60-73 - and this is the third carrier of those
# five values. NOT the first whose ordering the player sees: the eve's chain
# has always picked a paragraph by its own order.
# It WILL be the first to put the LADDER's ordering in front of the player as
# prose, once it is wired. Until then the ladder reaches the player only as piety
# and prestige, through the aftermath award. Do not "reconcile" the two.
#
# THIS CLAUSE READS THE BOND AND NOT THE CREED. bc_write_bond_effect also writes
# an orthogonal var:bc_battle_creed, which exists precisely because the ladder
# buries faith under nemesis/kin/countryman. So for a kinsman of another faith
# the faith fact is unsayable here. That is not an oversight: the creed gets its
# own clause class or it does not get said. Do not fold it into these five.
#
# THE FALLBACK NEVER RENDERS FROM THE TEN MOMENT TOASTS - and that is a claim
# about those ten call sites, not about the variable. bc_write_bond_effect writes
# bc_battle_bond on every one of its six paths - five ladder arms and the
# leaderless `else` - with no leading remove_variable, and bc_battle_open_effect
# calls it unconditionally (`bc_write_bond_effect = yes`, bc_ledger_effects.txt).
# All ten toasts run downstream of that call: seven commander sites in the same
# effect block, and three knight sites behind the same
# `scope:combat_side.side_commander ?=` link, which for bc_shieldbrother_forged
# is a SECOND block on that link rather than the same one
# (bc_knight_phase_events.txt:231 and :285). Either way a failed `?=` skips the
# open call and the toast together.
#
# DO NOT SHORTEN THAT TO "UNREACHABLE" AND DELETE THE ARM. A bond clause on a
# POP-UP OPTION's toast would reach it correctly whenever that option is answered
# after the combat ended: bc_clear_scratch_effect (bc_ledger_effects.txt) does
# `remove_variable = bc_battle_bond`, and eight of the mod's eighteen seam call
# sites are pop-up options, which the player may leave sitting in the queue.
# That file's THE ABSENT SIZE CASE IS REAL paragraph, above bc_wound_effect,
# records exactly this hazard for bc_battle_size, and states the same condition
# in the same words: `Answered after the combat ended`. Answered while the battle
# is still running - and the KNOWN LEAK paragraph says the leak reaches only a
# player who leaves a pop-up unanswered through the end of one - the variable is
# still there. So the arm is not routine; it is the tail, and the
# tail is real.
#
# THE STRING IS EMPTY because a path that left the variable unwritten could not
# name a foe, and every sentence in this class presumes one. Silence is the only
# honest output.
bc_bond_clause = {

# --- the scale, shared by all ten moments ------------------------------------
#
# bc_battle_size IS A NUMBER, NOT A FLAG, and this is the ONLY class in this file
# that compares one. The size ladder inside bc_battle_open_effect
# (bc_ledger_effects.txt) writes it with `value = 3` / `2` / `1`. Every other
# keyed class here compares `var:X = flag:y`. Writing `flag:huge` in an arm
# below would be a SILENT no-match - validate passes it clean, and the clause
# would simply never render. ON THE TOAST that is indistinguishable from a
# battle whose size was never written: both show nothing. IN THE LOG it is not.
# The ladder emits `BC: size 3` / `2` / `1`, so a size marker with no clause on
# the toast is this bug, and no size marker at all is the other one. Do not
# diagnose from the toast alone. Plan B task 3 step 4 has a mechanical check that
# reads both this definition and the writer and prints the two value lists; run
# it after touching either.
#
# THE ARMS COMPARE FOR EQUALITY, where every size gate elsewhere in the mod uses
# `>=` (bc_script_values.txt:114 and :118, the size gates inside
# bc_record_moment_effect and bc_wound_effect in bc_ledger_effects.txt,
# bc_eve_effects.txt:75). That is correct while the writer emits exactly 3, 2
# and 1 and nothing else, and the step 4 check is what keeps it correct. It is
# recorded because a fourth band would break the two forms differently, and
# NEITHER break is loud - validate passes both. A band added ABOVE the current
# top would make `>=` arms render the huge arm for it, which looks like ordinary
# prose and is wrong; these equality arms would render nothing at all, which
# looks like a battle whose size was never written. (A band added BELOW the
# current bottom fails IDENTICALLY in both forms - a `>= 3` / `>= 2` / `>= 1`
# ladder rejects 0 exactly as the equality arms do, and both fall to the
# trigger-less arm. It is a RENUMBERING that splits an existing range that sorts
# the two forms differently again.) Only the equality failure can be told apart
# from an unwritten variable, and only from the log: the `BC: size` markers name
# the band, so a marker for a band with no string is diagnosable, while a wrong
# string under a correct marker is diagnosable only by whoever already knows this
# mapping.
#
# THE BUCKETS ARE 10,000+ / 2,000+ / under, and they BELONG TO THE WRITER. The
# derivation, the measured distribution and the standing instruction not to
# re-guess the 2,000 boundary are all in the A BUCKET, 1/2/3 paragraph above the
# size ladder in bc_ledger_effects.txt. This file only names the three values the
# ladder writes; changing a boundary is an edit
# there, not here.
#
# THE THREE STRINGS GRADE ALONG ONE AXIS: how much of the fight is not yet in
# the fighting. Keep any rewrite monotone along it - two arms that make the same
# claim stop the clause carrying scale at all, which is the only thing it is for.
#
# THE ARM-BY-ARM GLOSS THAT USED TO SIT HERE IS DELETED ON PURPOSE. It named what
# each of the three strings said, and the strings live in bc_l_english.yml, so it
# went stale on every regrade and did: it still read `small, not a man` two
# regrades after that string was pulled for being a universal, and it survived
# two review rounds in that state while the twin summary in the loc file was
# corrected both times. A duplicated summary of three strings in another file has
# no reader who needs it. THE STRINGS AND THEIR REASONING LIVE IN ONE PLACE - the
# `shared fragments: the scale` section header in bc_l_english.yml, which is also
# where the smallest arm's must-not-be-a-universal rule is recorded. Read that
# before rewriting an arm; read this before rewriting the AXIS.
#
# THE SUBJECT IS BOTH HOSTS, NOT THE COMMANDER'S OWN MEN. The size ladder sets
# bc_battle_size by comparing num_total_troops on the COMBAT scope - and
# num_total_troops is a trigger, not a readable value (the A BUCKET, 1/2/3
# paragraph in bc_ledger_effects.txt), which is why the ladder compares rather
# than assigns. The combat is both sides. A clause phrased as a claim about
# his men would therefore report something the variable never measured, and would
# collide with the moments' own gates: bc_flank_collapses fires only when he is
# outnumbered (bc_commander_phase_events.txt:221) and bc_van_breaks_through only
# when he is outnumbering (:273).
#
# THE VERB HAS TO BE AGENTLESS AS WELL AS THE SUBJECT SHARED. Two drafts shipped
# and were pulled for this, and they are QUOTED rather than described, because
# describing them is how they got merged into one another in an earlier note:
#   b3e7c32  " Whole companies will be kept out of the fighting and never put in
#            at all."
#   4163d3b  " Whole parts of a battle this size are standing idle, not yet
#            called on."
# The first reads as the commander's OWN men, which on bc_flank_collapses
# contradicts a literal about a wing giving way for want of men. The second fixed
# the subject and not the verb: "called on" still implies someone who could have
# called and did not, and the toast carries that man's portrait. The three
# strings as shipped name no one who could have acted and did not.
#
# AND THE REPROACH DOES NOT NEED ADJACENCY TO LAND. The bond fragment renders
# BETWEEN the moment's literal and this clause on all ten toasts, and it always
# renders a SENTENCE there: bc_write_bond_effect writes on every path, so
# bc_frag_bond_any is unreachable from the ten toasts. bc_banner_falls_toast_desc
# additionally carries a ground CALL - the only desc that does, from Plan A's
# spike, and task 4 adds no others - but that call can resolve to the empty arm,
# because bc_write_ground_effect removes the variable first and has two exits
# that never rewrite it. See the paragraph at the top of this file, and the ten
# rewritten descs in Plan B task 4 step 1. DO NOT STATE A SENTENCE ORDINAL HERE:
# five of the ten literals are two sentences, so "the third sentence" and "the
# fourth sentence" have each been written into this file and each been wrong.
# What is checkable from one file, and what matters, is what renders in between.
#
# TWO OTHER AXES ARE CLOSED, AND BOTH WERE SHIPPED BEFORE THEY WERE CAUGHT.
# Read this before proposing a fourth rewrite, because both look free until the
# thing that owns them is named.
#
#   VISIBILITY - who hears about the moment - is owned by the ground fragments.
#   bc_frag_banner_falls_open reads ` There is nothing else on that field to
#   look at, and so they all see it go.`, and in the run of text task 4 builds
#   it renders AHEAD of this clause, so on open ground every scale arm either
#   restated it or contradicted it outright.
#
#   RECURRENCE - how often a fight this size throws up such a moment - is owned
#   by bc_chronicle_flag_days_value (bc_script_values.txt:110-128), which grades
#   off THIS VERY VARIABLE: size 3 gives a 10-day chronicle cooldown, size 2
#   twenty, size 1 forty. Prose putting two more moments in one afternoon does
#   not merely duplicate that value, it contradicts it by an order of magnitude,
#   and the player falsifies it by watching the screen.
#
# THE TEST FOR A REPLACEMENT AXIS IS FOUR ROWS, NOT ONE.
#
#   1. Settled by no other fragment class. Visibility failed here.
#   2. Settled by no mechanic keyed on bc_battle_size. Recurrence failed here;
#      grep the mod for `bc_battle_size` before believing an axis is free.
#   3. Contradicted by no moment's own `is_valid`. The commitment axis failed
#      here in its first phrasing - see the paragraph above on both hosts. Grep
#      the phase-event files for `bc_side_is_outnumber`, which is where that
#      failure was found. Grepping them for bc_battle_size returns one hit and it
#      is a comment (bc_knight_phase_events.txt:230); NO moment gates on the
#      variable, which is exactly why row 2 has to be a separate grep of the
#      whole mod rather than of these two files.
#   4. Reads the same after ALL TEN toast literals, because this clause is
#      shared.
#
# ROW 4 IS THE ONE AN AXIS ABOUT THE MOMENT CANNOT PASS. At least seven of the
# ten READ as states or one-offs rather than as repeatable events: a standard
# falls, ground favours you for the whole battle, a stalemate is a condition, a
# flank that does not stop bending is a condition too, a man is unhorsed onto his
# feet, a knight breaks and runs, a shieldbrother bond is forged.
#
# THAT IS A CLAIM ABOUT THE PROSE, NOT ABOUT THE EVENTS, and reading the
# `is_valid` blocks will not confirm it. NOTHING enforces once-per-battle on any
# of them: bc_banner_falls gates only on the chronicle cooldown, not faltering,
# and losing (bc_commander_phase_events.txt:39-43), while bc_rally_the_line
# requires faltering (:96-99) and clears it again through bc_rally_effect
# (bc_scripted_effects.txt:92-95), so banner, rally, banner is a reachable
# sequence inside one combat. The three knight moments are weaker
# still - they are `type = knight` (defined at bc_knight_phase_events.txt:50,
# :118 and :191; the `type` row is the line after each), so a second knight can
# do the same thing in the same fight, and the toast is written about the one man
# it fired for.
#
# The axis still fails, and it fails on the PROSE: a clause counting repetitions
# would be counting something these ten sentences never establish, and on the
# knight moments it would be counting a different man's moment than the one the
# toast describes. These three strings say nothing about the moment at all,
# which is how they pass.
#
# THE FALLBACK, LIKE bc_bond_clause'S, IS UNREACHABLE FROM THE TEN MOMENT TOASTS
# AND REACHABLE FROM A POP-UP OPTION'S. The ladder is an if/else_if/else, so it
# writes on all three paths with no leading remove_variable, and it sits above
# bc_write_bond_effect in the same effect - so every argument in bc_bond_clause's
# header applies here unchanged. bc_ledger_effects.txt's THE ABSENT SIZE CASE IS
# REAL paragraph makes the pop-up case for THIS variable by name: `Answered
# after the combat ended, it runs after bc_clear_scratch_effect and there is no
# bc_battle_size to read.`
#
# NOTHING CALLS THIS YET. Wiring it into the ten toasts is Plan B task 4.
