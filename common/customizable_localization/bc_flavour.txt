# Battle Chronicles - prose fragments.
#
# THE ARMS ONLY COMPARE A RECORDED CLASSIFICATION. Every classification decision
# was made in an effect - bc_write_ground_effect and bc_write_bond_effect in
# bc_context_effects.txt, the size ladder inside bc_battle_open_effect in
# bc_ledger_effects.txt - where it could be logged. Nothing here decides
# anything; it selects a sentence for a decision already recorded. So a fragment
# that renders wrong is two different bugs, and the marker in the log tells them
# apart: if the marker names the band you expected, the fault is in this file -
# arm order, comparison value, comparison form, or loc key - and if it does not,
# the effect classified wrong and this file rendered faithfully. Do not narrow
# the first half to arm order: the scale header below documents a fault of the
# comparison FORM that leaves the marker correct and the arm order correct.
#
# MOST OF THOSE COMPARISONS ARE AGAINST A FLAG. bc_scale_clause is the exception
# and compares a NUMBER, because bc_battle_size is written as one. Its own header
# says what that costs.
#
# CITATIONS INTO bc_ledger_effects.txt NAME A PARAGRAPH, NOT A LINE, AND THAT IS
# A RULE RATHER THAN A STYLE. That file's comments are long and get edited often,
# so every edit shifts every line below it. Rounds 7 and 8 both spent their
# headline finding on prose that had ROTTED rather than on prose that was wrong
# when written, and round 8's was this exact failure. In 253e4f7 two comments
# grew by three lines between them; most of the citations below were re-pointed
# correctly and a handful were not, and the ones that were not landed on an
# `exists` guard, a debug_log line, a paragraph tail, and the `A BUCKET, 1/2/3`
# heading itself. Read the commit if the detail matters. No count appears here
# on purpose: three rounds running, this paragraph asserted how many were wrong
# and was itself wrong, because the answer depends on whether a bare `:472`
# continuing a previous citation counts as one. That is the whole argument in
# miniature - a number about line numbers is as brittle as the line numbers.
#
# A name like `THE ABSENT SIZE CASE IS REAL` or `A BUCKET, 1/2/3` cannot rot
# silently: grep either finds it or the paragraph was renamed, which is a
# visible event. Note that landing on a heading is not the same as naming one,
# and only the name is checkable. `validate` now flags a citation that lands on
# a blank line, a bare `#`, a `}` that is not the end of a range, off the end of
# a file or below line 1, a range that runs backwards, a `bc_` file this mod
# does not have, and - as a warning - a basename more than one file here
# carries. The authoritative list lives in tools/ck3lib/validate.py, under
# `WHAT THIS CHECKS IS POSITION, NOT MEANING` - and a paragraph name is cited on
# one line or it is not cited at all, because a name broken across a line break
# is invisible to the grep that is the whole point of naming it. 631a6a9 wrote
# that rule, after 20ce50d had wrapped three of the four names it installed.
# Rounds 14 and 15 then each found wrapped names that the PREVIOUS round's sweep
# was supposed to have caught, and each time the sweep was file-wide in prose and
# partial in fact - 631a6a9 scoped by which commit had touched the name, fb6f4f0
# by what a name LOOKS like, and its ALL-CAPS detector could not see
# `Family 3 is shipped but unmeasured`, whose target is a markdown heading. So:
# the rule is REPO-WIDE the moment it is written down, and the acceptance test
# must be CASING-BLIND. REPO-WIDE IS NOT A FLOURISH. The sweep that accepted
# 137f93a ran over the mod directory only, while the prose beside it said
# `every commentable file`; the docs tree it never entered was carrying wrapped
# log markers the whole time - `BC: eve ground missing` in the live depth spec,
# `BC: combat end cleanup`, `BC: floor admitted` and `BC: style award` in the
# closed expansion plans, the engine's own `Duplicate localization key` in the
# handoff, and its
# `Compiling source for bc_record_moment_effect failed for unknown arguments: SWING`
# in the expansion design - which is the case the `engine message` half of the
# exemption boundary below was written for. The same shape as 631a6a9's sweep
# and fb6f4f0's, wide in prose and narrow in fact, one directory wider.
#
# THE DETECTOR IS AN UNBALANCED BACKTICK, which is casing-blind, needs no list of
# names, and is the literal signature of the defect rather than a proxy for it. A
# wrapped span leaves an odd backtick count on the line where the break starts
# and on the line where it ends; a line lying wholly INSIDE a span carries no
# backtick at all and is not flagged, so a span broken twice is caught at its two
# ends and not in its middle, and two independent unbalanced spans on one line
# sum to even and hide each other. Neither has occurred; both would need a
# different detector. Skip fenced code blocks, prune `.git` and `__pycache__`,
# and check every commentable file in both repos.
#
# IT IS A SCRIPT NOW, tools/sweep_backticks.py in the tooling repo, because the
# hand-rolled version was retyped from memory every round and was wrong in a new
# way each time. Its own header carries the limits above, and two FIXES the
# ad-hoc versions did not have. A fence opened inside a blockquote reads as prose
# unless the `>` prefix is allowed for, and WHAT THAT COSTS IS THE DELIMITER,
# NOT THE BODY: a delimiter is three backticks, so an unrecognised one is odd
# and reports itself, which is how the reputation plan's blockquoted fence
# turned up in a report. Its fenced body was scanned too and holds no backtick
# at all. And an escaped backtick has to be stripped before counting: counted
# raw, one inside an otherwise balanced line flips it to odd, which is noise,
# and one inside a genuinely unbalanced line flips it to EVEN, which is a miss.
# Stripping removes BOTH; it does not trade one for the other. The script
# spells its own backticks as escapes for the same reason
# - a detector that names its own source on every run teaches the reader to
# skim the report. Its tests spell theirs the same way, through named
# constants, and for the same reason: written literally the fixtures put a
# block of the test file into the report on every run. No number of constants
# is given, for the reason no number of citations is given above.
#
# AND IT IS PINNED, which is the half that makes the rest of this paragraph
# worth reading. tools/tests/test_sweep_backticks.py holds a test per claim
# made above - including the body half. That one needed a fixture whose body
# is ITSELF unbalanced: the blockquoted fence the reputation plan actually
# carries has no backtick anywhere in its body, so against that fixture alone
# the assertion cannot tell an exempt body from a body with nothing to say.
# Beside it, tools/tests/mutate_sweep_backticks.py breaks the script one line
# at a time and records which tests go red.
#
# BE PRECISE ABOUT WHAT THAT BUYS, because the first draft of this paragraph
# was not. Every mutant is killed and no test is left unkilled, and NEITHER
# FACT IS A STATEMENT ABOUT ANY SINGLE TEST. Both are properties of the pair
# taken whole, and a test can hold them while pinning less than its name
# claims. Round 18 found two such tests, and round 19 found another by the
# same method: writing mutants the harness did not have rather than re-running
# the ones it did. Its find is the sharpest illustration of the point - a test
# named for the extension list drew both its fixtures AND its expectation from
# that list, so deleting an extension deleted the fixture that would have
# caught it. THE MUTANT LIST IS THE CLAIM, and it is only as good as its
# coverage of the file it points at; for a collection, that means breaking each
# element SINGLY as well as wholesale. What this rules out is the shape the
# citation checker's own suite was twice found to have, a test that passes
# against a build with the checked behaviour deleted. What it does not rule out
# is a behaviour nobody thought to break - AND ONE SOMEONE THOUGHT TO BREAK AND
# THEN WROTE DOWN AS UNBREAKABLE. Round 20 recorded two deletions as
# deliberately absent from the harness, on the ground that each survives
# anyway. Round 21 found one of the two grounds false: NTFS collates uppercased
# and case-insensitively, which is not the order Python's sort gives, so both of
# the walk's sorts were observable all along and neither was observed. A list of
# decisions is the last place anyone re-reads, which is what makes a false
# premise parked in one durable.
#
# Two things about it are worth knowing before running it. First, it is NOT a
# validate check, and deliberately - the mod has legitimate multi-line
# quotations, of loc text and of script, and those wrap on purpose, so a hard
# error would fire on a clean tree. No count of them is given, for the reason a
# count of citations is not given above. THE EXEMPTION IS A QUOTED RUN OF TEXT; A
# GREP TARGET IS NEVER EXEMPT. The line between them is what the span is FOR: a
# marker, an engine message or a paragraph name exists to be pasted into a
# search, and wrapping it destroys the only thing it does; a run of script, a
# command line, a path or borrowed prose is read in place, and wrapping it costs
# nothing. What survives the sweep on a clean tree is all of the second kind.
# Second, a sweep that looks for a cited name and then goes looking for its
# definition is VACUOUS unless it excludes the citing
# line: a citation matches itself, so every name resolves and the sweep reports
# clean on a tree that has wrapped names in it. That shape was tried in the round
# 137f93a closed and did exactly this, which is why it is written down as a
# property of the shape rather than as a thing some past commit did.
#
# AND THE RULE COVERS LOG MARKERS, NOT ONLY PARAGRAPH NAMES. That is what the
# backtick detector turned up that no earlier sweep had: `BC: nickname awarded`
# and `BC: terrain NONE MATCHED` were both wrapped in README.md. A marker is a
# grep target twice over - once against this source, once against the game's own
# log - and a wrapped one cannot even be pasted into a log search.
#
# AND A SUFFIX OF A MARKER IS A GREP TARGET TOO. 8a0d33e claimed the opposite -
# that the `rule off` this sweep unwrapped in README.md was `NOT a marker`, a
# mere suffix under the `BC: nemesis` shorthand that section uses, and that
# `Unwrapping a suffix does not make it pasteable`. Both halves are wrong.
# `BC: nemesis rule off` is a live marker, written at
# bc_rivalry_effects.txt:77, and the README sentence that carried the wrapped
# text calls `decrement`, `cleared`, `wipe` and `rule off`
# `All four are permanent markers` in as many words. A suffix is a CONTIGUOUS
# SUBSTRING, so it pastes into a source grep and into a log grep and finds the
# marker; wrapped, it pastes into neither. The shorthand is a readability
# hazard and not a grep hazard, and this detector correctly does not care about
# it. The same reasoning covers `win not notable`,
# `fired bc_knight_holds_the_breach` and `subject AI`, all unwrapped in the
# docs tree for the same reason and all correctly unwrapped.
#
# Where the target's own heading wraps, prefer renaming the heading to fit one
# line over citing a prefix, since a prefix is itself a rot risk - which is what
# 137f93a did to the eve's order-disagreement heading. And check whether the
# adjacent paragraph is the better citation before assuming the wrapped one was
# meant, which is the mistake fb6f4f0 made and 137f93a undid. What `validate`
# cannot flag is a citation landing on the wrong LIVE line, which is the case
# round 8 lost its headline to.
# Not `--strict`: that flag only adds the missing-loc check, and the citation
# check runs on every validate.
#
# THE RULE IS ABSOLUTE FOR bc_ledger_effects.txt AND ASPIRATIONAL EVERYWHERE
# ELSE, and saying so is more honest than a rule this file breaks. Below there
# are still line citations into bc_script_values.txt, bc_eve_effects.txt,
# bc_scripted_effects.txt and the two phase-event files, and none of those is
# edited rarely either - bc_script_values.txt has 8 commits,
# bc_commander_phase_events.txt 7, bc_knight_phase_events.txt 8. That list is
# not exhaustive: the exemption below is deliberately outside it. No count of
# the citations appears here, because the count depends on whether a bare `:472`
# continuing a previous citation is one, and no single grep settles it - `.txt:`
# finds the full citations and misses every bare continuation. They get
# converted as the paragraphs around them are touched, not in a sweep, because a
# sweep of citations is the exact edit that went wrong in round 8 - and the ones
# 20ce50d converted, into bc_context_effects.txt, had been three lines stale
# since aef7f41, the very commit that wrote this rule. Anchor by SHA, never by
# "this round": 20ce50d wrote "the five that this round converted" truthfully
# and 631a6a9 inherited the phrase while converting something else entirely.
# For same-file references the rule is already absolute: name the key.
#
# ONE EXEMPTION, and it is not a loophole: a citation recording where a marker
# WAS in a build that has since moved on. The README section headed
# `Family 3 is shipped but unmeasured` does this - it quotes a log line against
# line 258 of a superseded bc_ledger_effects.txt and labels it a previous build.
# A paragraph name cannot express a pointer into a superseded file, and the
# number is not a claim about the current one. Anything that IS a claim about
# the current file follows the rule.
#
# THAT EXEMPTION IS WRITTEN WITHOUT THE `file:line` PUNCTUATION, and 2026-08-17
# is why. `validate` machine-checks every citation in that shape against the
# CURRENT file, so a historical pointer written in it is a time bomb: the line
# happened to be non-empty for months and a comment edit in the ledger shifted
# the file five lines and turned both copies of this note into hard errors.
# Prose the checker cannot parse is the correct form for a claim about a build
# that no longer exists.
#
# type = character ON EVERY DEFINITION, and invoked on a SAVED SCOPE, never on a
# variable-held character. Vanilla's Custom2 second argument is always a saved
# scope or ROOT.Char - a variable-held character has zero uses in vanilla or
# AGOT - so the mod does not use Custom2 at all.
#
# THE FALLBACK ARM IS LAST AND CARRIES A COMPLEMENT TRIGGER. It did not always:
# under first-match a trigger-less last arm is unreachable while a band matches,
# and every definition in this file used to end in one. **NO BANDED DEFINITION
# HAS A TRIGGER-LESS ARM as of 2026-08-17** - all thirteen banded definitions
# take `random_valid = yes`, and under `random_valid` a trigger-less arm is valid on
# EVERY render and takes a share of every toast to print nothing.
#
# THE RULE IS ABOUT MIXING, NOT ABOUT BARE ARMS. The five aftermath clauses at
# the end of this file are pure pools - every arm trigger-less, no fact being
# selected, only a wording - and that is correct and not an exception. What is
# forbidden is a bare arm sitting among banded ones, because it competes with
# all of them on every render. Their header carries the same argument.
#
# THE FIRST-MATCH RULE IS STILL WORTH KNOWING because it explains the shape of
# what is here: CK3 takes the first matching arm in order, so under first-match
# a trigger-less arm anywhere but last would swallow the ones below it. Both
# rules point the same way - the fallback goes last - and they disagree only
# about whether it may be bare. Under `random_valid` it may not.
#
# HOW OFTEN THAT FALLBACK ACTUALLY RENDERS VARIES BY DEFINITION AND BY CALL SITE.
# The ground case is stated here rather than in bc_banner_falls_ground's header,
# which is a spike marker and says nothing about its fallback; every definition
# added from bc_bond_clause onward states its own. On the ground clauses the
# fallback is load-bearing from anywhere, because bc_write_ground_effect removes
# the variable first and has two exits that never rewrite it. On bc_bond_clause
# it never renders from a moment toast at all, because bc_write_bond_effect
# writes on every path and runs upstream of every one of them - but it would render from a
# pop-up option's toast whose option is ANSWERED after the combat ended, because
# that is the case in which bc_clear_scratch_effect has already run - see the
# `KNOWN LEAK` paragraph above that effect in bc_ledger_effects.txt. Note the
# verb: what the close of that paragraph calls the normal case is the pop-up
# ARRIVING mid-battle, and a pop-up answered when it arrives still finds the
# variable there. No pop-up option toast exists yet.
#
# SO CHECK THE WRITER **AND** THE CALL SITE. Checking only the writer gives the
# wrong answer for the pop-up case, and no fallback here may be deleted on the
# strength of a claim that names only one of the two.
#
# NESTED, NOT SIBLING, on the variable read. The bare `exists` row and the
# trigger_if are safe as siblings - only the READ has to be nested, which is
# what the trigger_if does. A `trigger_if` whose `limit` fails evaluates TRUE,
# so the bare `exists` beside it is the row that actually rejects.

# --- the bond, shared by all ten moments -------------------------------------
#
# SHARED AND NOT PER-MOMENT, unlike the per-moment ground clause above (one so
# far, and a spike). A clause about the foe reads the same after a banner falling
# as after a flank collapsing; a clause about the ground does not - a standard
# goes down IN the sand, a flank collapses AMONG the trees. The verb has to agree
# with the ground and does not have to agree with the foe. That is the whole
# reason this is one definition and the ground will be ten.
#
# FIVE VALUES, MATCHING bc_write_bond_effect'S LADDER EXACTLY: nemesis, kin,
# countryman, heathen, stranger. `stranger` gets a real clause rather than
# sharing the fallback because it is a real answer, and the reason is the LADDER'S
# TERMINAL ARM, not the leaderless one. In bc_context_effects.txt, the paragraph
# `THE LADDER HAS A TERMINAL ARM AND IT IS NOT DECORATION` records that a foe of
# a different culture and the same faith - the largest match-up class on the AGOT
# map - lands there. The outer `else` in bc_write_bond_effect, the one that logs
# `BC: bond nofoe`, routes a LEADERLESS enemy side to the same value, but that
# arm justifies itself by saying the prose has a stranger clause, so citing it
# alone argues in a circle. It is also only one half of the value, and the
# smaller one. The same file's `MARKERS: SIX bond markers` paragraph warns not to
# read `nofoe` as a subset of `stranger` but as the OTHER half of it, and the
# terminal arm is the half that carries the largest match-up class.
#
# THE ORDER OF THOSE FIVE IS NOT THE ORDER THE EVE USES, deliberately. The eve's
# desc chain runs nemesis, kin, heathen, countryman, stranger; the ladder in
# bc_write_bond_effect runs nemesis, kin, countryman, heathen, stranger. This
# clause renders whatever the LADDER decided, so a same-culture different-faith
# foe now reads `countryman` in the toasts and `heathen` in the eve, in the same
# battle. That is the documented intent, and both halves of the
# reciprocal pair are written down: bc_context_effects.txt carries the paragraph
# `DO NOT "RECONCILE" THIS LADDER WITH THE EVE` and bc_eve_events.txt carries
# `THAT SPLIT IS VISIBLE TO THE PLAYER INSIDE ONE BATTLE`, which is the
# half making the same-battle claim. The order disagreement itself is documented
# in that same file, directly above that half, under the paragraph named
# `THE FOE CHAIN AND THE BOND LADDER DISAGREE ON ORDER, ON PURPOSE`. This clause
# is the last of the three carriers of those five values to be written, and
# NOT the first whose ordering the player sees: the eve's chain has always picked
# a paragraph by its own order. It IS the first to put the LADDER's ordering in
# front of the player as prose: Plan B task 4 wired it into all ten toasts.
# Before that the ladder reached the player only as piety and prestige, through
# the aftermath award. Do not "reconcile" the two.
#
# THIS CLAUSE READS THE BOND AND NOT THE CREED. bc_write_bond_effect also writes
# an orthogonal var:bc_battle_creed, which exists precisely because the ladder
# buries faith under nemesis/kin/countryman. So for a kinsman of another faith
# the faith fact is unsayable here. That is not an oversight: the creed gets its
# own clause class or it does not get said. Do not fold it into these five.
#
# THE FALLBACK NEVER RENDERS FROM THE TEN MOMENT TOASTS - and that is a claim
# about those ten call sites, not about the variable. bc_write_bond_effect writes
# bc_battle_bond on every one of its six paths - five ladder arms and the
# leaderless `else` - with no leading remove_variable, and bc_battle_open_effect
# calls it unconditionally (`bc_write_bond_effect = yes`, bc_ledger_effects.txt).
# All ten toasts run downstream of that call: seven commander sites in the same
# effect block, and three knight sites behind the same
# `scope:combat_side.side_commander ?=` link, which for bc_shieldbrother_forged
# is a SECOND block on that link rather than the same one
# (bc_knight_phase_events.txt:231 and :285). Either way a failed `?=` skips the
# open call and the toast together.
#
# DO NOT SHORTEN THAT TO "UNREACHABLE" AND DELETE THE ARM. A bond clause on a
# POP-UP OPTION's toast would reach it correctly whenever that option is answered
# after the combat ended: bc_clear_scratch_effect (bc_ledger_effects.txt) does
# `remove_variable = bc_battle_bond`, and eight of the mod's eighteen seam call
# sites are pop-up options, which the player may leave sitting in the queue.
# That file's THE ABSENT SIZE CASE IS REAL paragraph, above bc_wound_effect,
# records exactly this hazard for bc_battle_size, and states the same condition
# in the same words: `Answered after the combat ended`. Answered while the battle
# is still running - and the KNOWN LEAK paragraph says the leak reaches only a
# player who leaves a pop-up unanswered through the end of one - the variable is
# still there. So the arm is not routine; it is the tail, and the
# tail is real.
#
# THE STRING IS EMPTY because a path that left the variable unwritten could not
# name a foe, and every sentence in this class presumes one. Silence is the only
# honest output.
# THREE STRINGS PER VALUE INSTEAD OF ONE, 2026-08-17, AND `random_valid = yes`.
#
# WHY. This clause renders after EVERY moment toast, and the 2026-08-15 sweep
# counted 233 firings in 44 battles against five bond strings, of which two -
# stranger 134, countryman 126 - carried the bulk. A player fighting one war
# read the same sentence dozens of times. The keyed values are unchanged and
# the ladder is untouched; only the number of ways each value can be said has
# gone from one to three.
#
# `random_valid = yes` IS VANILLA, not an invention: 00_animal_custom_loc.txt's
# RandomElephantName and SmallAnimal both use it, and both are read from event
# descs that sit on screen, so re-evaluation on redraw is a shipped behaviour
# and not a hazard this mod discovered.
#
# THE FALLBACK NOW CARRIES AN EXPLICIT TRIGGER AND THAT IS NOT OPTIONAL.
# Without `random_valid` the arms were first-valid, so a trigger-less last arm
# could only be reached by falling through the five. WITH it the engine picks
# uniformly among ALL valid arms, and a trigger-less arm is valid always - so
# the empty string would have won roughly one render in four and silently
# deleted a clause that was available. `NOT = { exists = var:bc_battle_bond }`
# is exactly the condition the header above already states the empty string
# stands for, so this makes the arm say what it always meant.
#
# THE FIVE GROUPS REMAIN MUTUALLY EXCLUSIVE, which is what makes the random
# safe: var:bc_battle_bond holds exactly one flag, so the valid set is always
# the four variants of one value, never a mix of two.
#
# EVERY VARIANT OF A VALUE MUST MAKE THE SAME CLAIM. They are four ways of
# saying one fact the ladder already decided, not four degrees of it. This is
# the bond's version of the monotonicity rule the scale clause's header states,
# and it is the one thing a new variant can get wrong without anything
# catching it.
#
# EVERY VARIANT NAMES ITS SUBJECT. The toast carries the COMMANDER's portrait
# but a large minority of the moment literals are about a KNIGHT - the knight
# file holds thirty-one of the mod's seventy-four templates today - so a clause
# saying a bare `he` would attach to the wrong man on every one of them. `The man
# commanding here` is the shared frame and it is deliberate repetition.
#
# THE SCALE CLAUSE DID GET THE SAME TREATMENT IN THE END, AND THIS PARAGRAPH
# USED TO ARGUE THAT IT COULD NOT. The argument was that its header closes two
# axes outright and requires the strings to grade monotonically along a third,
# and that the loc file requires `not yet in the fighting` VERBATIM - so any
# variant would differ by a few words and buy nothing. The mistake was reading
# the verbatim requirement as binding on the WHOLE pool rather than on the
# original arm of each band: what it protects is that the three originals grade
# legibly against each other in one reading, and a variant that says something
# else entirely about the same band does not touch that. The scale clause now
# has five arms per band on exactly that basis. The four-row test in its header
# is still what a new arm has to pass; this paragraph never was.

# keyed class here compares `var:X = flag:y`. Writing `flag:huge` in an arm
# below would be a SILENT no-match - validate passes it clean, and the clause
# would simply never render. ON THE TOAST that is indistinguishable from a
# battle whose size was never written: both show nothing. IN THE LOG it is not.
# The ladder emits `BC: size 3` / `2` / `1`, so a size marker with no clause on
# the toast is this bug, and no size marker at all is the other one. Do not
# diagnose from the toast alone. Plan B task 3 step 4 has a mechanical check that
# reads both this definition and the writer and prints the two value lists; run

#

# recorded because a fourth band would break the two forms differently, and
# NEITHER break is loud - validate passes both. A band added ABOVE the current
# top would make `>=` arms render the huge arm for it, which looks like ordinary
# prose and is wrong; these equality arms would render nothing at all, which
# looks like a battle whose size was never written. (A band added BELOW the
# current bottom fails IDENTICALLY in both forms - a `>= 3` / `>= 2` / `>= 1`
# ladder rejects 0 exactly as the equality arms do, and both fall to the
# trigger-less arm. It is a RENUMBERING that splits an existing range that sorts
# the two forms differently again.) Only the equality failure can be told apart
# from an unwritten variable, and only from the log: the `BC: size` markers name

#
# THE TEN ORIGINAL MOMENTS EACH NAME THEIR OWN BAND AND THE OTHER TWENTY-SIX
# TOASTS NAME NOTHING. Plan B gave every one of the ten a per-moment ground set
# - bc_banner_falls_ground and the nine like it above - because those ten fire
# constantly and a shared sentence would have been read hundreds of times. The
# templates written since then got bond and scale and no ground at all, so a
# player reading bc_the_old_wolf or bc_knight_the_glory_hound is told who the
# foe is and how big the field is and never once told what is underfoot.
#
# ONE SHARED SET FOR ALL OF THEM, AND THAT IS THE RIGHT TRADE HERE. A per-moment
# set for twenty-six more toasts would be a hundred and fifty-six strings, and
# each of those toasts fires far less often than any of the ten - they are gated
# on a trait, an age, a foe or a battle condition, where the ten are gated on the
# battle going one way or the other. Rare toasts can share a sentence; common
# ones cannot.
#
# FOUR PER BAND, RAISED FROM TWO, AND THE REASON IS THE CALL COUNT AND NOTHING
# ELSE. When the set was written it was called by twenty-six toasts and two
# arms was a defensible ration; it is now called by SEVENTY-FIVE, and a player
# whose war is being fought on rough ground reads one of two sentences on every
# moment toast for the length of it. The command that produced that number, run
# from the mod root:
#   grep -o "Custom('bc_ground_clause')" localization/english/bc_l_english.yml | wc -l
#
# THE OLD HEADER GAVE A DIFFERENT REASON FOR TWO AND THE REASON WAS SOUND -
# a band's sentence has to stay true of every terrain the band collects, and the
# bands were partitioned for prose rather than for tactics, so `rough` has to
# survive hills, mountains, wetlands and bog at once, where the bond and scale
# clauses have no such constraint because a nemesis is a nemesis. That argument
# caps what a string may SAY. It never capped how many of them there could be;

# it exactly as the first twelve were. Anything a reader can picture on a
# mountain and not in a bog does not belong in `rough`.
#
# WHAT THIS SET MAY NOT SAY. It renders after a literal that already described a
# man doing something and before a clause about the foe, so every string here is
# about the GROUND and never about the men on it, and none of them may claim a
# consequence. The per-moment sets can say the slope broke the charge because
# they know what the charge was; this one does not know what happened.
#
# IT IS NOT CALLED BY ANY OF THE TEN. Doubling a ground clause onto a desc that
# already has one would print two sentences about the same field, and the
# per-moment string is the better of the two every time. Nor is it called by the
# seven toasts that are GATED on a band - bc_winter_bites and the six like it
# already spend their whole literal on the ground.
#
# THE FALLBACK IS A COMPLEMENT, for the reason bc_scale_clause's header gives at
# length: under `random_valid` an untriggered arm is valid on every render and
# would take a share of every toast to print an empty string.
# ===========================================================================

# ===========================================================================
# THE AFTERMATH CLAUSES, 2026-08-17.
#
# EVERY MOMENT TOAST IN THE MOD ENDS IN THREE POOLED CLAUSES AND NOT ONE
# AFTERMATH TOAST DID. bc_rivalry_*_desc, bc_dead_knights_toast_desc and
# bc_wounded_toast_desc are the prose a player reads at the END of a battle -
# the part that is supposed to be memorable - and each of them was a single
# fixed sentence pair that never varied over a whole campaign.
#
# A POOL OF TRIGGER-LESS ARMS IS THE CORRECT SHAPE HERE, and it is the shape
# this file spent a whole batch REMOVING from the ground sets. The rule is not
# "no trigger-less arm"; it is that a trigger-less arm must not sit in a
# definition whose other arms are banded, because under `random_valid = yes`
# it is valid on every render and takes a share of every toast. Where EVERY
# arm is trigger-less the definition is a pure pool and that is exactly what
# is wanted: no fact is being selected, only a wording.
#
# NO ARM MAY NAME A CHARACTER, A HOUSE, A PLACE OR THE GROUND. The descs that
# call these already print the names from saved scopes, and a fragment that
# tried to would be reaching for a scope this file has never touched. Every
# arm below is one sentence that is true of any battle in the game.
#
# THE CLAUSE IS APPENDED, NOT SUBSTITUTED. The fixed sentence keeps saying the
# fact - who lost to whom, how many times, who is on the field - and the
# clause only says what it means. Same division of labour as the moment
# toasts, where the desc carries the moment and the three clauses carry the
# ground, the bond and the scale.
# ===========================================================================
