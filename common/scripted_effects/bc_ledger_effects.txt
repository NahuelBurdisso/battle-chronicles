# Battle Chronicles - the ledger.
#
# ONE SEAM. Every moment in the mod — phase event or pop-up option — reports
# itself through bc_record_moment_effect and nothing else writes moment state.
# That is the only place the "state never lives inside a toast" rule has to be
# enforced, the only place the variable leak surface has to be audited, and the
# only place a future system has to hook.
#
# ALL WRITES LAND ON THE SIDE COMMANDER. Every `type = knight` event roots on
# the knight, so they call in from inside scope:combat_side.side_commander ?= .
# THE COUNT IN THIS PARAGRAPH USED TO BE THREE and is now thirty-one; it is
# written without a number on purpose, because the rule is the type and not the
# tally. `grep -c '^bc_.* = {' common/combat_phase_events/bc_knight_phase_events.txt`
# is the count if one is wanted.
# NOTHING IN THIS MOD EVER WRITES A bc_ VARIABLE ONTO A KNIGHT. Per-character
# state on every participant has to be cleared on both sides or it leaks forever,
# and there are far more knights than commanders.
#
# THREE TIERS OF STATE:
#   momentum  character modifier  20 days, wiped at combat end
#   scratch   character variable  this battle only, cleared at combat end
#   ledger    character variable  forever
# Momentum must stay a modifier — it is what the engine reads for advantage.
# Scratch and ledger must be variables — bc_cleanup_effect strips every modifier
# at combat end, so anything modifier-shaped cannot persist by construction.
#
# CLEARING MEANS remove_variable, NEVER set_variable value = 0. Six of the nine
# scratch variables cannot hold zero (enumerated at bc_clear_scratch_effect
# below), and absence-versus-zero is load-bearing: it is how
# the seam detects the first moment of a battle and which arm of the pacing floor
# fires.

# --- opening the battle -----------------------------------------------------
#
# Called UPSTREAM OF EVERY READ in every commander and knight phase event -
# before bc_mark_chronicle_effect and before any trigger_event, where
# scope:combat_side always exists. Not literally at the top of every `effect`
# block; see the THE ANCHOR comment on save_scope_as = bc_chronicle_subject below
# for the knight events, all of which call it nested.
#
# UNCONDITIONAL, NOT WRITE-IF-UNSET. An earlier design skipped when the variables
# were already set. That was wrong for a reason outside this effect: scratch is
# cleared at combat end on `side_commander`, so a commander REPLACED mid-combat is
# never cleared — and under write-if-unset his stale values would freeze
# PERMANENTLY, not for one battle. A stale bc_battle_size of 3 would let a
# two-hundred-man skirmish maim people once family 3 ships.
#
# Overwriting is also MORE correct on the foe: capturing the current enemy
# commander at every phase event tracks a mid-battle replacement on the other
# side, which capture-once does not.
#
# CALL THIS AT MOST ONCE PER EVENT EXECUTION. The `?=` below leaves
# scope:bc_open_foe untouched when it fails rather than clearing it, so a second
# call in the same execution whose `?=` failed would find the FIRST call's scope
# still standing, pass the `exists` test, and write the wrong foe. No call site in
# plan 1 calls it twice — all ten call it exactly once per execution, seven at the
# top of the `effect` block and three nested, per THE ANCHOR comment below — but
# plan 4 adds code to this same effect, so the constraint is written down rather
# than left to be rediscovered.
bc_battle_open_effect = {
	# THE ANCHOR. Every context writer below reaches into a province or reads a
	# foe, and both rebind the scope. This is the only handle on the commander
	# that survives those hops. It carries no meaning of its own - it is an
	# address, not a fact - so it is exempt from the "no saved scope carries
	# meaning" rule in the spec, and a stale one is harmless because it is
	# rewritten in every phase event, before anything reads it. NOT literally at
	# the top of every effect block: the seven commander events call this effect
	# at the top, but the knight events call it nested inside their
	# `scope:combat_side.side_commander ?=` block (bc_knight_phase_events.txt:101,
	# :169, :232). Upstream of every read is what matters, not the line number.
	save_scope_as = bc_chronicle_subject

	scope:combat_side.enemy_side.side_commander ?= {
		save_scope_as = bc_open_foe
	}
	if = {
		limit = { exists = scope:bc_open_foe }
		set_variable = {
			name = bc_battle_foe
			value = scope:bc_open_foe
		}
	}
	else = {
		# Self-contained: without this, a leaderless enemy side leaves the
		# PREVIOUS battle's foe in place. bc_clear_scratch_effect (task 12)
		# happens to cover this today, but that is a different effect in a
		# different task, and this one should not depend on it.
		remove_variable = bc_battle_foe
	}

	# A BUCKET, 1/2/3 — never a raw troop count.
	#
	# num_total_troops is a TRIGGER ONLY: triggers.log:9537-9540 gives it
	# comparison traits and scope `combat`, it appears in no value log, and all
	# four of its uses in the playset are left-hand trigger comparisons. There is
	# no way to read it into a set_variable value =. An earlier design wrote
	# `value = scope:combat_side.combat.num_total_troops`, which would simply not
	# have worked, and every size gate in the expansion rested on that one write.
	#
	# NOT side_strength, which IS readable and is therefore the trap:
	# bc_script_values.txt:15-16 records that the engine scales it down by 1000, so
	# reaching for it would make every battle read as "under 2,000".
	#
	# 10,000 is bc_battle_is_notable_trigger's own lower size row — the
	# `combat = { num_total_troops >= 10000 }` row of that trigger in
	# bc_scripted_triggers.txt, cited by the trigger's name rather than by line
	# because that line number has already rotted once, when the band wrappers
	# were inserted above it. 2,000 was INVENTED — the calibration run
	# recorded `under 5k` as one undivided bucket and never subdivided it. It was
	# then measured over 143 battles, counted per side against the world rather
	# than against this variable: 5k+ 46, 3k 42, 2k 31, 1k 14, under-1k 4. The
	# boundary STANDS — it splits the low band 73/18 instead of leaving one lump,
	# which is the whole point of having it. Do not re-guess it; re-derive it by
	# restoring the ladder from git history, the same rule the README states for
	# the aftermath thresholds.
	#
	# THE THREE MARKERS ARE PERMANENT AND THEY REPLACE DIAG Q3. Q3 measured the
	# WORLD; these measure what the MOD CHOSE, and the whole risk in spec Section 6
	# is that those two disagree. Without them there is no way at runtime to tell a
	# size-1 battle from a size-3 one, and every claim in plans 2-6 about big
	# battles behaving differently becomes unmeasurable.
	if = {
		limit = { scope:combat_side.combat = { num_total_troops >= 10000 } }
		set_variable = { name = bc_battle_size value = 3 }
		debug_log = "BC: size 3"
	}
	else_if = {
		limit = { scope:combat_side.combat = { num_total_troops >= 2000 } }
		set_variable = { name = bc_battle_size value = 2 }
		debug_log = "BC: size 2"
	}
	else = {
		set_variable = { name = bc_battle_size value = 1 }
		debug_log = "BC: size 1"
	}

	# --- context: what this battle is ---------------------------------------
	#
	# AFTER the size ladder and BEFORE the eve raise at the bottom. The eve reads
	# what these write, and the size ladder writes what one of them reads.
	bc_write_ground_effect = yes

	# AFTER the foe block at the top of this effect - it reads var:bc_battle_foe,
	# which that block writes or removes. AFTER the dead-nemesis housekeeping
	# would be better still, but the housekeeping sits below and moving it is a
	# larger change than this needs: bc_facing_nemesis_trigger carries its own
	# `is_alive = yes` row, so a dangling reference fails to match and falls
	# through to the next arm. The consequence is one phase event of a dead man's
	# grudge reading as `countryman` or `stranger` rather than `nemesis`, which is
	# the correct answer anyway.
	bc_write_bond_effect = yes

	# --- housekeeping: drop a dead nemesis ----------------------------------
	#
	# HOUSEKEEPING, NOT SAFETY. Every bc_nemesis read is already guarded by
	# `exists` plus `is_alive = yes`, and a dead character is a real object in
	# CK3, so is_alive on one is a clean `no` rather than an error.
	#
	# WHAT THIS ACTUALLY FIXES: bc_rivalry_loss_effect's first arm tests
	# `NOT = { exists = var:bc_nemesis }`, so a commander holding a dead
	# reference can never acquire a new nemesis. One dead foe would disable C
	# for that commander permanently.
	#
	# HERE RATHER THAN AT THE READ SITES because both read sites are pure
	# TRIGGER contexts - a phase event's is_valid and an event desc branch - and
	# no effect runs in a trigger. This effect is the one place an effect is
	# guaranteed to run on the commander during a battle.
	#
	# IT LAGS THE READ BY ONE PHASE EVENT, harmlessly: is_valid runs before the
	# effect block, so the first roll of the first battle after the man dies
	# still reads the dangling variable. The guard handles that read cleanly.
	#
	# NESTED, NOT SIBLING. `exists = var:bc_nemesis` beside a read of
	# var:bc_nemesis would be a missing-variable read on every commander in the
	# world who has no nemesis, on every phase event roll - which is most of
	# them.
	#
	# Both variables go together. Leaving bc_nemesis_losses behind would let the
	# next grudge inherit the dead man's counter and start at `rival`.
	#
	# THIS DOES NOT REMOVE THE RELATION. A relation with a dead man is CK3's own
	# business. The variables are the mod's; the relation is not.
	if = {
		limit = { exists = var:bc_nemesis }
		if = {
			limit = { NOT = { var:bc_nemesis = { is_alive = yes } } }
			remove_variable = bc_nemesis
			remove_variable = bc_nemesis_losses
			debug_log = "BC: nemesis wipe"
		}
	}

	# THE OPENING IS RAISED HERE, AND IT IS RAISED LAST ON PURPOSE. Everything it
	# reads is written above: var:bc_battle_foe by the foe block at the top of this
	# effect, var:bc_battle_size by the ladder in the middle. The dead-nemesis
	# housekeeping directly above must also have run first, so that a battle
	# against a man who died last year cannot name him.
	#
	# IT FIRES ITSELF ONLY ONCE PER BATTLE. bc_eve_offer_effect's own gate is
	# `NOT = { exists = var:bc_battle_moments }`, and this effect runs on every
	# moment - see that file's header for why that idiom means "first moment".
	#
	# IT USED TO RUN FROM on_combat_start AND COULD NOT WORK THERE. No commander is
	# assigned to a combat side at that point, measured over 22 combats. This is
	# the earliest place the mod can reach a side commander at all.
	bc_eve_offer_effect = yes
}

# --- the seam ---------------------------------------------------------------
#
# bc_record_moment_effect = { TIER = minor|major|decisive  KIND = <kind>  SWING = up|down }
#
# TIER as passed is the REQUESTED tier. The escalation ladder below is a CEILING
# and can only lower it — a site asking for `minor` on the tenth moment still gets
# `minor`. That is why exactly two call sites request `decisive`: a ceiling cannot
# manufacture a tier nobody asks for.
#
# SWING exists because polarity is real in the shipped events and neither of the
# other two parameters carries it. bc_horse_killed_under_him and
# bc_van_breaks_through are both KIND `bloodied`, and one falters while the other
# gains. The wound gate in plan 6 is written against SWING = down.
#
# NO COMBAT SCOPE IS TOUCHED HERE. Eight of the eighteen call sites are pop-up
# options, and bc_events.txt records as an invariant that those character events
# hold no combat scope at all. Everything combat-scoped lives in
# bc_battle_open_effect instead.
#
# EVERY PARAMETER A CALL SITE PASSES MUST BE READ SOMEWHERE IN THE BODY, or the
# whole effect fails to compile and every call site is silently dead. The first
# live run of this file shipped $SWING$ in the signature and read it nowhere,
# which produced
#   [E] Compiling source for bc_record_moment_effect failed for unknown
#       arguments: SWING          bc_ledger_effects.txt line: 119
# thirteen times at load, zero `BC: moment` lines in the whole session, and no
# other symptom - no toast broke, no event stopped firing, nothing at the call
# sites complained. That is why the swing arms below exist: plan 6's wound gate
# is written against SWING = down and needs the parameter to survive until then,
# so the cheapest legal read is a two-arm log. Deleting these two branches
# re-breaks the entire seam.
bc_record_moment_effect = {
	if = {
		limit = { NOT = { exists = var:bc_battle_moments } }
		set_variable = { name = bc_battle_moments value = 1 }
	}
	else = {
		change_variable = { name = bc_battle_moments add = 1 }
	}

	# flag:$SWING$ = flag:down, not $SWING$ = down - same idiom, and for the same
	# reason, as the tier comparison documented below.
	if = {
		limit = { flag:$SWING$ = flag:down }
		debug_log = "BC: moment swing down"
	}
	else = {
		debug_log = "BC: moment swing up"
	}

	bc_record_effective_tier_effect = { TIER = $TIER$ KIND = $KIND$ SWING = $SWING$ }

	# Family 2 needs a real battle. Size 1 is a skirmish and gets the tide only -
	# spec Section 6, "verb families gate on size".
	#
	# NESTED, NOT TWO SIBLING ROWS IN ONE `limit`. CK3 does not short-circuit and
	# guarantees no evaluation order among siblings, so
	# `limit = { exists = var:bc_battle_size  var:bc_battle_size >= 2 }` would
	# still evaluate the comparison when the variable is absent and log a read of
	# a missing variable.
	#
	# THE ABSENT CASE IS REAL, NOT DEFENSIVE PADDING. Eight of the eighteen call
	# sites are pop-up options, and a pop-up answered AFTER combat ended has had
	# bc_battle_size removed by bc_clear_scratch_effect. Without this guard that
	# option would log an error - and if the comparison somehow passed, it would
	# apply a 20-day modifier that bc_cleanup_effect has already run past and will
	# never remove.
	if = {
		limit = { exists = var:bc_battle_size }
		if = {
			limit = { var:bc_battle_size >= 2 }
			bc_apply_verb_effect = { KIND = $KIND$ SWING = $SWING$ }
		}
	}
}

# The ceiling, then the style write. Split out of the seam only because the
# ceiling has to resolve BEFORE the style comparison can use it — the style is
# keyed on EFFECTIVE tier, not requested.
#
# The ceiling is read AFTER bc_battle_moments is incremented, so the first moment
# of a battle sees 1, not 0, and there is no zero case.
#
#   moments 1-2  ->  minor
#   moments 3     ->  major
#   moments 4+   ->  decisive
#
# THE DECISIVE RUNG WAS 5 AND IT WAS MEASURED TOO HIGH. Across two logged runs
# (874 moments, ~80 combat ends) `decisive` fired exactly ONCE. The reason is that
# battles average about 4.2 moments, so a floor of 5 sat ABOVE the mean and the
# rung was not rare, it was very nearly unreachable - which also meant family 3's
# wound, which hangs off this arm alone, could never be measured at all.
#
# 4 IS THE MEAN, NOT A GUESS. It puts the rung at roughly the length of a typical
# battle, so a decisive moment needs a battle that ran a little long rather than
# one twice the usual length. **Re-measure before moving it again** - the next run
# is the first with any decisive data at all, and the major band is now a single
# moment wide, which is the part most likely to need a second look.
#
# THE COMPARISON IS `flag:$TIER$ = flag:decisive`, NOT `$TIER$ = decisive`. A bare
# `$TIER$ = decisive` substitutes textually to `decisive = decisive`, and `decisive`
# is not a script value, trigger or scope anywhere in vanilla, AGOT or the playset —
# it is an unknown key, which is a silent no-op, not a validation failure. Wrapping
# both sides in `flag:` is the shipped idiom for comparing a parameter against a
# literal: vanilla 00_animal_effects.txt:1659 (`flag:$BONUS$ = flag:court_physician`)
# and :1778-1793 (`flag:$METHOD$ = flag:gift` and two siblings), AGOT
# 00_agot_character_data_effects.txt:1427-1463. Call sites are unaffected — they
# still pass TIER = decisive.
bc_record_effective_tier_effect = {
	if = {
		limit = {
			flag:$TIER$ = flag:decisive
			var:bc_battle_moments >= 4
		}
		bc_write_style_effect = { RANK = 3 KIND = $KIND$ }
		debug_log = "BC: moment decisive"

		# Family 3 hangs here and ONLY here. This arm IS the effective tier: it is
		# the point at which the ceiling has already been applied and the answer is
		# `decisive`. bc_wound_effect's header explains at length why the obvious
		# alternative - reading var:bc_battle_tier - is wrong.
		#
		# LAST IN THE ARM ON PURPOSE. Effects in a block run top to bottom, so
		# "BC: wound" can only ever be written AFTER the "BC: moment decisive" that
		# caused it. The two counts are read as a ratio and that ordering is what
		# makes the pairing legible in a 500k-line log.
		bc_wound_effect = { SWING = $SWING$ }
	}
	else_if = {
		limit = {
			OR = {
				flag:$TIER$ = flag:decisive
				flag:$TIER$ = flag:major
			}
			var:bc_battle_moments >= 3
		}
		bc_write_style_effect = { RANK = 2 KIND = $KIND$ }
		debug_log = "BC: moment major"

		# THE MAJOR ARM WOUNDS TOO, AND IT IS THE ARM THAT DOES THE WORK.
		# Measured 2026-08-15: the whole mod asks for `decisive` exactly ten
		# times a run, all ten from bc_flank_collapses, and seven of those ten
		# arrive while the ledger still holds 1-2 moments, so they demote to
		# minor. Decisive resolved ONCE in 44 battles. Hanging the wound off
		# that arm alone gave it a single opportunity in a 500k-line log, which
		# is why "BC: wound" read zero for three runs while nothing was
		# actually broken - the rung above it was starving it.
		#
		# Major resolved 45 times in the same run. Same arm shape, same $SWING$,
		# and bc_wound_effect's own var:bc_battle_wounded guard still caps it at
		# one wound per battle, so this widens the sample without widening the
		# outcome.
		bc_wound_effect = { SWING = $SWING$ }
	}
	else = {
		bc_write_style_effect = { RANK = 1 KIND = $KIND$ }
		debug_log = "BC: moment minor"
	}
}

# bc_battle_style holds the KIND of the HIGHEST-TIER moment of the battle, ties
# broken by the LAST such moment. Not last-wins: a decisive stand on day five
# should name the battle even if a minor scuffle followed it.
#
# `>=` rather than `>` is exactly what makes ties break to the last moment. Do not
# "tidy" it to `>`.
#
# This needs a high-water mark, which is what bc_battle_tier is for. It cannot be
# derived from bc_battle_moments, because a call site may request `minor` at any
# rung of the ladder.
#
# THE ABSENCE CASE IS A SEPARATE BRANCH, NOT AN `OR` ROW. Writing it as
# `OR = { NOT = { exists = var:bc_battle_tier }  var:bc_battle_tier <= $RANK$ }`
# looks equivalent and is not: CK3 does not short-circuit, so on the first moment of
# every battle — when the variable does not exist yet — the second row still
# evaluates and logs a read of a missing variable, once per moment, forever. The
# mod already states this rule in its own source, in the imperative — see the
# comment above the nickname gate in `bc_chronicles.0091`: "Do not rely on
# evaluation order to make it safe - CK3 guarantees no order of evaluation among
# siblings, in a limit or anywhere else."
# The nested shape below is the same one `bc_notable_battle_counter_effect` uses.
bc_write_style_effect = {
	if = {
		limit = { NOT = { exists = var:bc_battle_tier } }
		set_variable = { name = bc_battle_tier value = $RANK$ }
		set_variable = { name = bc_battle_style value = flag:$KIND$ }
	}
	else_if = {
		limit = { var:bc_battle_tier <= $RANK$ }
		set_variable = { name = bc_battle_tier value = $RANK$ }
		set_variable = { name = bc_battle_style value = flag:$KIND$ }
	}
}

# --- family 3, the flesh ----------------------------------------------------
#
# bc_wound_effect = { SWING = up|down }
#
# CALLED FROM THE DECISIVE AND MAJOR ARMS OF bc_record_effective_tier_effect, AND
# NOWHERE ELSE. That placement IS gate 1a: an arm is the definition of "this moment
# resolved to that tier", after the ceiling has been applied. It was decisive-only
# until 2026-08-15; the major arm carries the comment explaining why it is not.
#
# DO NOT REWRITE THIS AGAINST var:bc_battle_tier. The spec says to and the spec is
# wrong on that one word. bc_battle_tier is a HIGH-WATER MARK - bc_write_style_effect
# above only ever writes it upward, so once any moment of a battle has been
# decisive it reads 3 for the rest of the battle. Gating on it would let a MINOR
# moment wound a commander because a decisive one happened six moments earlier.
#
# THE COMMANDER, ALWAYS. Every seam call site in bc_knight_phase_events.txt sits
# inside a `scope:combat_side.side_commander ?= { }` block, which plan 1 task 11
# step 4 asserts and plan 6 task 5 re-asserts. wounded_1 carries
# `disables_combat_leadership = yes`; landing it on a courtier knight - of which
# one battle produces 41 rolls - is the failure this whole chain prevents.
#
# `flag:$SWING$ = flag:down`, NEVER `$SWING$ = down`. A bare comparison substitutes
# textually to `down = down`, an unknown key, which is a SILENT NO-OP that validate
# passes - every wound would fire regardless of swing. Same failure as
# `$TIER$ = decisive`; same shipped fix (vanilla 00_animal_effects.txt:1659).
#
# THE SWING ROW STOPPED BEING INERT ON 2026-08-15. It was: both TIER = decisive
# call sites pass SWING = down, so while this ran off the decisive arm alone the
# row rejected nothing. The major arm feeds it every KIND the mod raises, and the
# 2026-08-15 run logged 24 + 16 `BC: moment swing up` against 47 + 17 + 16 + 12 +
# 10 down - so roughly a third of what now reaches here is a WIN. This row is the
# only thing standing between that and wounding a man for winning.
#
# THE SIZE READ IS NESTED, THE OTHER FOUR ROWS ARE NOT. CK3 does not short-circuit
# and guarantees no evaluation order among siblings, so a comparison in the outer
# limit would evaluate even when the variable is absent. `exists`, `has_trait`,
# `has_game_rule` and a flag comparison are all safe on absence; only
# `var:bc_battle_size >= 3` is a read.
#
# THE ABSENT SIZE CASE IS REAL. bc_chronicles.0001 opt c is one of the two decisive
# call sites and it is a POP-UP OPTION. Answered after the combat ended, it runs
# after bc_clear_scratch_effect and there is no bc_battle_size to read.
#
# max = 1 IS THE LINE THAT KEEPS "DEATH NEVER". rank is a DELTA (effects.log:3507),
# `wounded` is a real trait group (AGOT 00_traits.txt:6346), and max caps the new
# rank. The has_trait guard makes this a no-op on an already-wounded man; max = 1
# makes the ceiling structural, so the mod cannot create a wounded_2 even if the
# guard is later loosened. A mod-created wounded_2 would put a commander one
# VANILLA wound from wounded_3, which is the doorway to every lethal path in
# 20_health_effects.txt - indirectly lethal while satisfying "death never" in
# letter.
#
# NO DURATION, NO TIMED REMOVAL, NO RECOVERY EVENT. Vanilla's
# wounded_recovery_pulse (AGOT health_on_actions.txt:369) fires four times a year
# off yearly_health_pulse and triggers on `has_trait = wounded`, so a raw
# change_trait_rank inherits the entire recovery system for free. Anything written
# here to take the trait away would race it.
#
# bc_battle_wounded IS SET INSIDE THE INNER `if`, NOT THE OUTER ONE. It records
# that a wound HAPPENED, not that one was considered. Setting it outside would let
# the first decisive-and-down moment of a SMALL battle block the wound for the rest
# of that battle - a bug that would only ever show up as "wounds are rarer than the
# gates say".
bc_wound_effect = {
	if = {
		limit = {
			flag:$SWING$ = flag:down
			NOT = { has_game_rule = bc_wounds_off }
			NOT = { exists = var:bc_battle_wounded }
			NOT = { has_trait = wounded }
			exists = var:bc_battle_size
		}
		# DIAGNOSTIC, AND IT COMES OUT ONCE THE RATIO IS KNOWN. Same rule the eve
		# and the dead knights each cost a run to learn: one marker in the
		# innermost block cannot say which gate rejected. This one splits the
		# five-row outer limit from the size read, which are the two candidates
		# with different fixes.
		debug_log = "BC: wound gates passed"
		if = {
			limit = { var:bc_battle_size >= 3 }
			change_trait_rank = {
				trait = wounded
				rank = 1
				max = 1
			}
			set_variable = { name = bc_battle_wounded value = yes }
			debug_log = "BC: wound"

			# STATE FIRST, PRESENTATION SECOND. The trait, the variable and the
			# marker are all written before the toast, per the rule
			# bc_knight_phase_events.txt:18-24 records from the first live run:
			# effects nested inside a send_interface_toast are not trustworthy for
			# an AI character, and most commanders in the world are AI.
			#
			# THE save_scope_as IS NOT OPTIONAL. bc_addressed_toast_effect writes
			# `left_icon = $SUBJECT$`, a scripted effect does not rebind ROOT, and
			# its liege arm has already changed scope by the time left_icon is
			# evaluated - so SUBJECT must be a SAVED SCOPE, never `this`.
			#
			# THIS TOAST IS THE WHOLE NOTIFICATION. wounded_1 carries
			# `flag = no_message` (AGOT 00_traits.txt:6330), so the trait arrives
			# with no vanilla message of any kind. Without this block a commander
			# silently stops being able to lead armies and nothing on screen says
			# why.
			save_scope_as = bc_wounded_commander
			bc_addressed_toast_effect = {
				TYPE = event_toast_effect_bad
				TITLE = bc_wounded_toast
				DESC = bc_wounded_toast_desc
				SUBJECT = scope:bc_wounded_commander
			}
		}
	}
}

# --- scratch clearing -------------------------------------------------------
#
# remove_variable, NEVER set_variable value = 0. Six of the nine cannot hold
# zero — bc_battle_style is a flag, bc_battle_foe is a character,
# bc_battle_wounded is a presence test, bc_battle_ground is a flag,
# bc_battle_bond is a flag, bc_battle_creed is a flag — and absence-versus-zero
# is what the seam and the pacing floor both test.
#
# KNOWN LEAK, not closed here. A pop-up answered AFTER the battle has already
# ended writes scratch that nothing will clear: bc_chronicles.0001/0002/0003 are
# player events sitting in the queue, so if the combat resolves before the player
# clicks, the option's bc_record_moment_effect runs after this effect has already
# run, leaving bc_battle_moments, bc_battle_tier and bc_battle_style behind.
# bc_battle_open_effect overwrites bc_battle_size and bc_battle_foe on the next
# battle but does NOT touch those three, so the next battle starts with an
# inflated moment count and a stale style. It affects only a human player who
# leaves a pop-up unanswered through the end of a battle, and the obvious fix —
# having bc_battle_open_effect clear all three — has to be weighed against the
# pop-up legitimately arriving mid-battle, which is the normal case and must keep
# working.
bc_clear_scratch_effect = {
	remove_variable = bc_battle_moments
	remove_variable = bc_battle_tier
	remove_variable = bc_battle_style
	remove_variable = bc_battle_size
	remove_variable = bc_battle_wounded
	remove_variable = bc_battle_foe
	remove_variable = bc_battle_ground
	remove_variable = bc_battle_bond
	remove_variable = bc_battle_creed
}

# --- family 2: the character of the fight -----------------------------------
#
# The leaf, mirroring bc_add_momentum_effect in bc_scripted_effects.txt so that
# duration lives in exactly one place per family. 20 days, the same as momentum:
# both families are wiped at combat end by bc_cleanup_effect, so the duration
# only matters for the pre-existing case of a pop-up answered after the battle
# ended - see the KNOWN LEAK note on bc_clear_scratch_effect above.
bc_add_verb_effect = {
	add_character_modifier = {
		modifier = $MODIFIER$
		days = 20
	}
}

# The (KIND, SWING) -> modifier table. THIS IS THE ONLY PLACE THE MAPPING LIVES.
#
#   bloodied    either  ->  bc_bloodied
#   entrenched  either  ->  bc_shieldwall
#   wild        either  ->  bc_spent_horse
#   ordered     up      ->  bc_pursuit
#   ordered     down    ->  nothing
#   adapted     either  ->  nothing
#   measured    either  ->  nothing
#
# NO `else` ARM. adapted and measured are the KINDs that describe how the
# commander READ the battle rather than what the battle DID to the army, and
# there is no army modifier that means "he judged it well". ONE HUNDRED AND
# FORTY-TWO of the four hundred and twenty-five call sites are adapted or
# measured - the five plan 1 shipped (bc_ground_favours_us, bc_lines_bogged_down
# and the pop-up options .0001b, .0002b and .0003b) plus one hundred and
# thirty-seven from later content batches - and every one of them is supposed
# to fall through. Thirty-five more, all `ordered`/`down`, fall through the
# `ordered` row's else, so ONE HUNDRED AND SEVENTY-SEVEN sites in total get no
# modifier by design. A future `else` arm would silently start handing an army
# modifier to all of them.
#
# THE COMPARISON IS `flag:$KIND$ = flag:bloodied`, NOT `$KIND$ = bloodied`. A bare
# `$KIND$ = bloodied` substitutes textually to `bloodied = bloodied`, an unknown
# key, which is a SILENT NO-OP that validate passes cleanly - the whole ladder
# would be dead and nothing would say so. Same rule and same reason as the tier
# comparison in bc_record_effective_tier_effect; the precedents are cited there.
#
# ONLY THE `ordered` ROW TESTS SWING, AND THAT ASYMMETRY IS DELIBERATE. Do not
# "fix" it in either direction - neither by adding a SWING test to the other three
# rows nor by deleting it from this one.
#
# THE PAIR CENSUS, RE-COUNTED 2026-08-17 AND NO LONGER WHAT PLAN 1 WROTE. Plan 1
# shipped eighteen call sites using nine of the twelve (KIND, SWING) pairs and
# recorded `entrenched`/`down`, `wild`/`up` and `ordered`/`down` as unreachable.
# **ALL TWELVE PAIRS ARE NOW REACHED.** Counted mechanically over the whole mod
# at four hundred and twenty-five call sites:
#
#   measured/down 35  bloodied/up 36   ordered/up 35     wild/down 36
#   entrenched/up 35  bloodied/down 36  wild/up 35       adapted/up 36
#   entrenched/down 35  ordered/down 35  measured/up 36  adapted/down 35
#
# The table's BEHAVIOUR has not changed as those cells filled - it never asked
# about any pair but `ordered`'s. What changed is that plan 1's claim that a
# SWING test on entrenched or wild would be always-true or always-false is now
# simply false, and a reader who trusted it would "fix" this ladder on a premise
# the data stopped supporting.
#
# THE THREE LATE PAIRS ARE DELIBERATE AND THE CONSEQUENCE IS INTENDED. `wild`/
# `up` is a moment that grants momentum and blows the horses in the same breath -
# bc_the_wrath_takes_him and bc_the_old_grudge both hand the commander a rung and
# bc_spent_horse together, which is the whole point of calling them wild rather
# than bloodied. `entrenched`/`down` is a line that braces while it is losing and
# gets bc_shieldwall for it. `ordered`/`down` is a formation that keeps its shape
# while going backwards, or a pursuit that walks into trees and stops being one,
# and the right consequence for both is that bc_pursuit is simply not handed out.
# None of the three wants a SWING test here.
#
# `ordered` remains the one KIND where the design wants the pair, and both halves
# are reachable - thirty-three call sites use `up`, thirty-three use `down`.
#
# THE COUNTS IN THIS COMMENT GO STALE EVERY TIME A CONTENT BATCH LANDS. The
# command that produced them, run from the mod root:
#   grep -rho 'KIND = [a-z]* SWING = [a-z]*' --include=*.txt . | sort | uniq -c
# Two of the matches are this file's own definition and its usage comment, and
# neither carries a KIND, so the pair total is the call-site total.
#
# SWING IS STILL A PARAMETER OF THE SEAM, NOT OF THIS TABLE. Plan 6's wound gate
# reads it on every KIND, including the three this ladder ignores. Dropping it
# from the seam because this table barely uses it would break that plan.
#
# ALL FOUR MODIFIERS ARE REACHABLE, so an absent verb in testing is a bug and not
# a gap in the call sites. Re-counted 2026-08-17 across the whole mod, from the
# pair census above: bc_bloodied from 72 sites, bc_shieldwall from 70,
# bc_spent_horse from 71, bc_pursuit from 35, and 177 falling through. Those five
# sum to the four hundred and twenty-five, which is the check.
# (Plan 1's numbers were 3, 3, 4 and 3, when there were eighteen call sites.)
#
# THE MARKER STRINGS ARE LITERALS, NOT $KIND$. Two reasons. $PARAM$ substitution
# inside a quoted string eats the space in front of it, and more importantly a
# substituted marker would print the same text whether the ladder matched or fell
# through - which is the exact failure these markers exist to catch.
bc_apply_verb_effect = {
	if = {
		limit = { flag:$KIND$ = flag:bloodied }
		bc_add_verb_effect = { MODIFIER = bc_bloodied }
		debug_log = "BC: verb bloodied"
	}
	else_if = {
		limit = { flag:$KIND$ = flag:entrenched }
		bc_add_verb_effect = { MODIFIER = bc_shieldwall }
		debug_log = "BC: verb shieldwall"
	}
	else_if = {
		limit = { flag:$KIND$ = flag:wild }
		bc_add_verb_effect = { MODIFIER = bc_spent_horse }
		debug_log = "BC: verb spent horse"
	}
	else_if = {
		limit = {
			flag:$KIND$ = flag:ordered
			flag:$SWING$ = flag:up
		}
		bc_add_verb_effect = { MODIFIER = bc_pursuit }
		debug_log = "BC: verb pursuit"
	}
}
