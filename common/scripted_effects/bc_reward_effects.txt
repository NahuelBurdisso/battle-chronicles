# Battle Chronicles - the reward path.
#
# Everything here runs at COMBAT END, from the two combat-end graders - which task 6
# gathers into bc_aftermath_events.txt, one task after this one. The one exception is
# bc_addressed_toast_effect: it is generic routing, and later plans call it from
# mid-battle contexts too.
#
# Nothing else here runs during a battle. That is the split from
# bc_scripted_effects.txt, which is the opposite: momentum, cooldowns and
# chronicle pacing, all of which run mid-battle and none of which persists.
#
# ROOT in every caller is a COMBAT SIDE, not a character. Effects here that need
# to name a character in a toast take it as a saved scope.

# --- aftermath: the knight's memory of the field ----------------------------
#
# Called from inside `every_side_knight`, so THIS is the knight. One effect
# parameterised by $TYPE$ rather than two, matching bc_add_momentum_effect
# above - the won/lost split is a localization decision, not a behavioural one.
#
# random_memory, NOT scope:new_memory. Both scope:new_memory idioms are well
# shipped - twenty-odd sites write it directly, four re-save it into a second
# scope first with a comment calling it "a dark pact with Code" - but every one
# of those twenty-four is a single-character call in an event immediate, an
# option or a toast. NONE is inside an iterator, which is the only place this
# effect is ever called, so none of them proves scope:new_memory rebinds on
# each pass rather than sticking to the first memory created.
#
# random_memory does not care. It searches the memories of the character
# currently in scope, and the newly created one is the only memory of that type
# without battle_location set - every earlier one got the variable when it was
# made. There is no cross-pass scope to rebind and nothing to leak between
# knights. The randomness is nominal: the limit matches exactly one memory.
#
# Direct precedent, from the mod we load under: AGOT's
# death_in_battle_memory_effect (death_management_events.txt:2308-2349) is a
# $TYPE$-parameterised effect that creates a battle memory and sets this same
# battle_location variable this same way.

bc_battle_memory_effect = {
	create_character_memory = {
		type = $TYPE$
	}
	random_memory = {
		limit = {
			has_memory_type = $TYPE$
			NOT = { has_variable = battle_location }
		}
		set_variable = {
			name = battle_location
			value = scope:bc_battle_province
		}
	}
}

# --- aftermath: the commander's tally ---------------------------------------
#
# Notable battles WON, on side commanders only. Never cleared - that is the
# point, and it is why it lives on commanders rather than on every participant,
# keeping the leak surface to one variable on characters who lead armies.
#
# Distinct from vanilla's combat_event_0001_tracker, which counts CONSECUTIVE
# wins and resets to 0 on any defeat. This one is cumulative: it survives a
# defeat, it just does not grow on one.
#
# The create-or-increment shape is vanilla's, from combat_events.txt:90-107.
# change_variable on a variable that was never set is not safe.

bc_notable_battle_counter_effect = {
	if = {
		limit = { NOT = { exists = var:bc_notable_battles } }
		set_variable = {
			name = bc_notable_battles
			value = 1
		}
	}
	else = {
		change_variable = {
			name = bc_notable_battles
			add = 1
		}
	}
}

# --- aftermath: the name he wins --------------------------------------------
#
# THE POOL WAS ONE FLAT LIST OF 27 AND IS NOW SEVEN, 2026-08-17. Two separate
# changes, both about cases:
#
# 1. THE POOL WAS TOO NARROW. It took AGOT's first nickname group - the 27
#    "heroic" entries at 00_agot_generic_nicknames.txt:5-31 - and stopped
#    there. The file's THIRD group, :44-49, is
#    `the_anvil / the_tactician / the_trebuchet / the_warlord / the_battlemaster`,
#    which are more obviously names a man wins by COMMANDING than half of the
#    first group is. There was no reason to omit them beyond not having looked.
#    All five are added.
#
#    THE SECOND GROUP, :33-42, IS TAKEN ONLY IN PART. Four of its ten carry
#    `is_bad = yes` and are excluded outright - the caller's gate decided this
#    man earned something. Of the six that remain, three are prefixes or too
#    close to the is_bad four to read as a reward in general, and three -
#    `the_brute`, `the_beast`, `the_slaughterer` - are used ONLY in the
#    bloodied and wild ladders below. AGOT files them next to its insults, so
#    they belong where the man's own record already says he fought that way,
#    not in a pool every winner draws from.
#
#    NO `is_prefix = yes` KEY IS TAKEN from any group. `nick_agot_hard` and
#    `nick_agot_the_stone` render in front of the name rather than after it,
#    which is a different shape of result, and the mod has never produced one.
#
# 2. THE NAME NOW FITS THE MAN. It was a flat random_list, so a commander who
#    had spent three battles dug in behind a shieldwall was exactly as likely
#    to be called Fireball as a man who charged. The style ladder that already
#    exists on this character - var:bc_style_last, written by
#    bc_style_streak_effect in bc_reputation_effects.txt and never cleared - is
#    the obvious selector and cost nothing to read.
#
#    SIX LADDERS PLUS A FALLBACK, NOT PER-ENTRY WEIGHTS. Both shapes give the
#    same result; this one is legible and does not need 35 nested trigger_if
#    guards, one per entry, to read one variable safely.
#
#    NAMES REPEAT ACROSS LADDERS ON PURPOSE. `greysteel` fits entrenched,
#    measured and adapted alike, and each ladder is kept to eight entries or
#    more so that the style narrows what a man is called without making it
#    predictable.
#
#    THE FALLBACK IS THE FULL 32 AND IT IS REACHABLE. bc_style_last only
#    exists once the commander has fought a notable battle in which some
#    moment fired, and notability is independent of whether any moment fired
#    at all - the same gap bc_chronicles.0091's `BC: award no creed` marker
#    reports. A man can therefore reach the nickname gate with no style on
#    record, and he must still get a name.
#
# The keys are REFERENCED, not redefined, so the pool tracks AGOT if AGOT
# changes it.
#
# This is the only place mod script names an AGOT key. The dependency is not
# new - descriptor.mod already declares `dependencies = { "A Game of Thrones" }`.
# The mod's no-hard-dependency stance was always about OPTIONAL playset mods
# such as Seasons of Ice and Fire, which is why the terrain triggers use plain
# vanilla keys.
#
# give_nickname runs OUTSIDE the toast. A send_interface_toast body only
# reliably runs for a character a player is playing, and nearly every commander
# in the world is AI. State first, presentation second - the mod's own rule.
#
# NOT set_nickname_effect: that deliberately overwrites any nickname flagged
# is_bad (00_nickname_effects.txt:8-11), and a Westeros playset is full of
# bad-sounding canon names worth keeping.
#
# left_icon MUST be scope:bc_named_commander, NOT `root`. A scripted effect does
# not rebind ROOT, and the only caller is bc_chronicles.0091, which is
# `scope = combat_side` - so `root` here is the COMBAT SIDE, and left_icon only
# accepts a character, artifact, title, dynasty or house. The caller saves the
# scope. Same reason the phase events use scope:bc_commander / scope:bc_knight.

# --- addressed toasts -------------------------------------------------------
#
# A toast is ADDRESSED, not broadcast. Nearly every commander and every knight in
# the world is AI, and a toast raised on a man nobody is playing reaches nobody —
# so a toast ABOUT an AI subject is raised on somebody who might be human.
#
# Whether the toast BODY additionally executes for an AI character was an open
# question - README.md said both things in two different places. It was measured
# at combat end across 128 toasts whose subject was a non-player character, by
# splitting the count on `is_ai` OUTSIDE the toast and comparing to a marker
# inside it: human 0, AI 128, inside 128. THE BODY RUNS. README.md now records
# that next to the claim it corrects.
#
# This effect is correct either way - addressing is about who SEES the toast, not
# about whether its body executes, and those are independent. Only the strength of
# the "keep state out of toasts" rule depended on the answer, and that rule now
# rests on convention and legibility rather than on reliability.
#
# CALLED ON THE SUBJECT. Tests is_ai on THIS, raises on THIS or on `liege`.
#
# SUBJECT must be a SAVED SCOPE, never `this`. A scripted effect does not rebind
# ROOT, and in the liege arm the scope has already moved by the time left_icon is
# evaluated — so left_icon = $SUBJECT$ only names the right man if the caller
# saved him first.
#
# TYPE IS A PARAMETER AND IT IS REQUIRED. Not everything routed through here is
# good news: plan 4 announces the man who has beaten you twice and plan 5
# announces your dead knights. Hardcoding event_toast_effect_good would put a
# green tick on both. Callers pass event_toast_effect_good or
# event_toast_effect_bad - the mod already uses both (bc_banner_falls uses _bad).
#
# THERE IS NO DEFAULT. CK3 substitutes parameters textually and does not error on
# a missing one, so an omitted TYPE would emit the literal text `type = $TYPE$`
# and validate would pass it. Every call site names the type explicitly; the
# caller sweep in task 5 step 3 is what enforces it.
bc_addressed_toast_effect = {
	if = {
		limit = { is_ai = no }
		send_interface_toast = {
			type = $TYPE$
			title = $TITLE$
			desc = $DESC$
			left_icon = $SUBJECT$
		}
	}
	else_if = {
		limit = { exists = liege }
		liege = {
			send_interface_toast = {
				type = $TYPE$
				title = $TITLE$
				desc = $DESC$
				left_icon = $SUBJECT$
			}
		}
	}
}
